# 大区域地图管线（分析稿）

目标：用 MiraForge 现有的「场景 → 分层 → 按层出图 → 导出」机制，产出 Silksong / 银河城尺度的区域，而不是一张 1024 的插画。

对标工程：`E:\godot\abyss_reclaimer`（Godot 4.7，64px 网格，相机 zoom 1.5，视口 1920×1080）。
本文只做设计分析，不含代码改动。

---

## 0. 结论先写

1. **不要用「一张大地图 → 切开 → 每块重画」当主路径。** 这条路能出概念图，但切开的边界一定会裂：扩散模型守的是语义和构图，不守像素。
2. **把「大」拆成三个不同的东西分别解决**：区域（一张全景，只当风格/地图界面/光色脚本）、房间（布局骨架 + 玩法带）、屏幕格（1200–1500 px，MiraForge 真正画得好的尺度）。
3. **连续性靠结构，不靠像素**：视差背景按「整区域一条」生成（天然无缝），玩法带按格生成（缝落在柱子、拱门、岩唇、雾上），碰撞布局永远由 Godot 侧确定。
4. MiraForge 现有四个积木刚好够用：**场景 = 区域**、**图片 = 屏幕格**、**分层 = 视差层**、**局部编辑（inpaint）= 接缝修复**。真正缺的只有「格坐标」和「把 blockout 当参考图」两个小概念。

---

## 1. 两边的硬数字

### 1.1 Godot 侧（来自 `docs/05_地图与场景美术规范.md` 与工程实测）

| 项目 | 值 |
|---|---|
| 视口 | 1920×1080，相机 `zoom = 1.5` |
| 一屏可见世界 | **1280×720** |
| 网格 | 64×64，地图尺寸必须是 64 的倍数 |
| 普通房间目标 | 3×2 屏 = **3840×1536**（60×24 格） |
| 现存房间实测 | entry 2304×1152、crossroads 1792×768、gate/vault 1216×768、shrine 1024×768 |
| 区域目标 | 约 8192×2048 世界 |
| 视差 | far 0.07 / mid 0.26 / near 0.58 / 玩法 1.00 / 前景 1.10，Y 恒 1.0 |
| 角色尺度 | 玩家约 124 px 高，单跳 181 px，二段跳 362 px |

**关键推论：一屏世界只有 1280×720，而引擎会把世界像素放大 1.5 倍显示。**
也就是说，按「世界像素 1:1」生成 1280×720 的素材，上屏是 1.5 倍放大——对厚涂/手绘风完全可接受（现在 moon 素材就是 3 倍整数缩放）。不必为了 3840 的宽度去逼模型出 3840。

### 1.2 MiraForge / Qwen 侧

| 项目 | 值 / 现实 |
|---|---|
| 舒适出图 | 1024×576 ～ 2560×1104（现有产物多在这个区间） |
| 上限 | 能请求更大，但 Qwen-Image-2.1 的质量甜点在 1–2 MP；再大只会更糊，不会更「复杂」 |
| 每张耗时 | turbo 约 8–40 秒，非 turbo 约 1–2 分钟 |
| 透明 | 分层产物是真 RGBA，缩略图已改 PNG 保 alpha |
| 参考图 | 编辑链路最多 2 张（第 1 张定结构，第 2 张定风格/细节） |

**结论：MiraForge 的「画布」应该是一屏（1280×720），而不是一个房间，更不是一个区域。**

## 2. 为什么「切图各画一块」必然裂

一次生成 = 一次去噪采样。参考图给的是**语义与构图约束**，不是像素约束：

- 同样的边界像素，模型每次会重新解释边缘的材质、明度、遮挡关系；
- 两块拼起来，会出现三种典型裂缝：**明度台阶**（左右亮度差 5–15%）、**材质错位**（石缝/根须走向不接）、**遮挡错乱**（左边画了柱子但右边没接上）。
- 越靠近画面边缘，模型的注意力越弱，边缘自适应越强——所以**裂缝永远长在边界上**。

这不是调提示词能解决的问题，是方法问题。要么让边界不出现在画面里（结构法），要么让边界被重新生成本地化掉（修复法），要么两者一起用。

## 3. 四层防线：让接缝不可见

按成本从低到高，建议全上，但可以逐层叠：

### 防线 1：结构性切分（最重要，零成本）

**缝要落在本来就该断的地方**，而不是落在岩石中间：

| 可用断点 | 说明 |
|---|---|
| 立柱 / 拱门 / 门框 | 竖直构件天然切断画面，宽度 64–128 px |
| 岩唇 / 断崖 / 石台侧壁 | 地面高差本身就是一条线 |
| 垂挂根系 / 藤帘 | 竖向遮挡，宽度 64–192 px |
| 雾气带 / 水幕 / 瀑布 | 低对比，容错最高 |
| 暗部 / 通道口 | 纯黑或近黑区域 |

把这块写进房间规格：**每个屏幕格必须至少有一个可用断点与邻格相接**。切分时优先沿这些结构切，而不是沿 1280 的整数倍切。

### 防线 2：带重叠的条件生成

- 相邻格生成时留 **160–192 px 重叠**（约 15%）。
- 参考图给两张：**① 本格的 blockout 裁剪（结构）② 已生成邻格的重叠条（延续性）**。
- 提示词里写明「延续左侧已存在的立柱与地面线，不要改变轮廓」，并禁止「重新构图」。

MiraForge 的编辑链路正好支持两张参考图（第 1 张定结构，第 2 张定内容），这条现在就能用。

### 防线 3：多候选 + 自动挑缝

每格出 **2–4 张**（现有 `count` 参数就是干这个的），用 PIL 在重叠带上打分：

```text
score = 0.55 * mean(|ΔL| over band)          # 明度差
      + 0.25 * mean(|Δcolor| in Lab)         # 色相差
      + 0.20 * gradient_orientation_mismatch # 走向一致性
```

挑分数最低的那张。经验上这一步能把「明显裂」的概率从 ~60% 降到 ~15%，成本只是每格多跑 1–3 次。

### 防线 4：接缝局部重绘 + 全局调色

- **接缝重绘**：拼好后，沿每条缝开一个 256×256 的窗口、盖 32–48 px 的软遮罩，跑一次 `image_inpaint`，提示词「只修复接缝，保持两侧结构不变」。这是最可靠的一步，成本约每缝 20–40 秒。
- **全局调色**：整间房按参考全景做一次 LAB 直方图匹配，再加一层区域雾/暗角渐变。这一步专治「明度台阶」，而且能顺手统一整区氛围。

> 四层叠加后的实测目标：并排看找不到缝；跨屏走动时只有材质笔触差异，没有结构断裂。

## 4. 推荐管线（四段）

### 4.1 区域规格（数据，不是图）

一个区域先落成一份规格，MiraForge 的「场景」正好承载它：

```text
区域：废弃矿区（abandoned_mine）
  色板：冷蓝灰石构 + 深青环境光 + 青绿荧光 + 暖琥珀点缀
  高度层：3 层（上层根系枢纽 / 中层断桥网络 / 下层积水矿道）
  房间：entry, crossroads, gate, shrine, vault, 2 个随机槽位
  每房间：屏幕格数（3×2 / 2×3）、出口方位与高度、地标、可用断点
  视差：4 层，速度 0.07 / 0.26 / 0.58 / 1.10
```

这份规格有两个用途：给 LLM 出提示词、给 Godot 出房间资源（`RoomDefinition` 已有 `exits`/`connections` 字段，可直接扩展 `screens`、`landmark`、`seams`）。

### 4.2 布局骨架（blockout，先于美术）

在 64 网格上先画「能玩」的骨架，**用纯色块**：地面、墙、单向平台、坑、竖井、门洞。

- 来源二选一：Godot 里手摆（最稳），或按房间语法程序生成（3 层 + 1 闭环 + 1 支线 + 1 捷径，`docs/05` §2.4 已是现成语义）。
- 校验：单跳 ≤2 格、二段跳 ≤5 格、竖井贯通 ≥1 屏、出口不同高。
- 输出：`blockout.png`（本房间，3840×1536，纯色）+ 碰撞（TileMapLayer 直接锁死）。

**这一步决定了「复不复杂」。** 现在图「太简单」的根本原因不是分辨率，是布局里只有一条水平主线。

### 4.3 单元格出图（MiraForge）

不要一房间一张，按屏幕格出：

```text
房间 3×2 → 6 格，每格 1280×720（+160 px 重叠 → 生成 1440×880 再裁）
参考图 1：blockout 对应裁剪（放大到 1440×880）
参考图 2：相邻已生成格的重叠条
提示词：本格的层级角色 + 密度预算（见 §6）+ 断点位置
每格出 2 张，自动挑缝（§3 防线 3）
```

生成顺序建议 **蛇形**（左→右，下一行右→左），保证每格至少有一侧邻居已生成，第二张参考图永远可用。

**视差四层不在这里出。** 四层按 §5 单独整区域生成——这是省时又保连续的关键。

### 4.4 装配与模块化（Godot）

出图之后不是「贴上去」，而是拆成三种东西：

| 产物 | 来源 | 用法 |
|---|---|---|
| 玩法带地砖图集 | 从格子图里切 64px 平铺区域，或单独出一张 2048×2048 模块表 | TileMapLayer 换肤，碰撞不变 |
| 结构/道具/地标 Sprite | 从格子图里抠（MiraForge 分层已经是 RGBA） | `Environment/Structure`、`Props`、`Landmark` |
| 视差底图 | §5 的整区四层条 | `Visuals/*Parallax` |

这条分工和 `docs/05` §5 的「Tile / Sprite 分工」完全一致：**美术服从碰撞**，出图只是给碰撞换皮。

## 5. 视差层的数学（这是「大地图」真正的坑）

### 5.1 覆盖率

视差层在相机移动 `T` 世界像素时，自身只移动 `s·T`，所以画面里要「多出来」`(1-s)·T` 的素材。一屏 1280 宽时：

```text
所需素材宽 ≈ 1280 + (1 - s) * T
```

| 层 | s | 覆盖一个 3840 宽房间 | 覆盖 4 房间宽区域（15360） | 建议生成宽度 | 引擎缩放 |
|---|---:|---:|---:|---:|---:|
| 远景 | 0.07 | 4851 px | 15 565 px | 2048 | ×7.6 |
| 中景 | 0.26 | 4122 px | 12 646 px | 2048 | ×6.2 |
| 近景 | 0.58 | 2893 px | 7 731 px | 2048 | ×3.8 |
| 前景 | 1.10 | 896 px | — | 1280 | ×1.0 |

**远景要 15 000 px 宽才「不露边」，但远景不需要 1:1 细节**——它在屏幕上是低对比、低饱和、被雾包住的。所以远景按 1/7、中景按 1/6、近景按 1/4 生成再放大，视觉上完全站得住，成本从「不可能」变成「4 张图」。

### 5.2 跨房间连续

现在的写法是房间局部坐标：`scroll_offset = (camera - room_origin) * (1 - s)`。
房间各有原点，所以两个房间的远景在边界处对不上。

要连续只有两条路：

1. **整区共享一张**：四层都按「区域坐标」生成，每个房间放的是同一张图的**世界映射裁剪窗口**，`scroll_offset` 改成 `(camera_world - region_origin) * (1 - s)`。边界天然连续，代价是每房间要算裁剪矩形。
2. **每房间一张 + 边界遮断**：把房间边界设计成雾墙/瀑布/岩体，让远景的变化「合法」。成本低，但对设计有约束。

建议：**远景 + 中景用方案 1（只 2 张图管整个区域），近景 + 前景用方案 2（每房间一张，边界用结构遮断）**。

### 5.3 分层顺序很重要

按层生成（远/中/近/前各一条）比按格生成整图再切层更好：

- 每层的接缝容忍度不同（远景糊、前景硬剪影），可以分别处理；
- 整区一条 = 没有接缝；
- 前景永远是低矮剪影，本地生成即可，不需要连续。

## 6. 「太简单」怎么治：密度预算

复杂度是设计出来的，不是分辨率堆出来的。给每条提示词加**可数的指标**，比说十遍「复杂、宏大」有用：

| 指标 | 每屏建议 | 说明 |
|---|---:|---|
| 平台/可站立面 | 3–5 段 | 分布在不同高度 |
| 竖直构件（柱/拱/根帘） | 2–3 个 | 也是断点位置 |
| 地标构件 | 每房 1 个 | 全屏尺度，唯一 |
| 前景剪影覆盖 | ≥ 8% 且 ≤ 10% | 规范上限 10% |
| 玩法带明度对比 | ≥ 背景 2 倍 | 平台顶边必须清楚 |
| 色阶 | 5–7 色 + 1 强调色 | 每材质 ≤3 个明度台阶 |
| 视觉节奏 | 每 3 屏 1 个「空」+ 1 个「密」 | 留白是复杂度的另一半 |

把这些写进 LLM 的 system prompt（MiraForge 的「分层提示词」已经在做类似的事，可以复用同一套机制），比人肉写形容词稳得多。

## 7. 映射到 MiraForge 现有机制（几乎不用改引擎）

| 游戏概念 | 现在用哪个积木 | 缺什么 |
|---|---|---|
| 区域 | 场景（`scenes`） | 一张「区域全景」作为风格参考；四层条的归属 |
| 房间 | 场景下的一个分组 / 一个「房间」子对象 | 房间与格子的父子关系（或就用命名约定 `room_entry_c0r0`） |
| 屏幕格 | 一张图（`images`） | **格坐标**（room, col, row）与重叠参数 |
| blockout | 参考图（`image_edit` 的第 1 张） | 让「布局图」能作为参考上传（现在只能传场景图） |
| 视差四层 | 分层方案（`layer_sets`） | 按「区域」而不是「单图」建方案 |
| 接缝修复 | 局部编辑（`image_inpaint`） | 自动生成遮罩的批处理（沿缝开窗） |
| 导出 | ZIP + manifest | 按 Godot 单位输出（世界坐标、64 网格对齐、层速度） |

也就是说：**要做的是「编排」，不是「新引擎」**。最小增量是「格坐标 + blockout 参考 + 批量接缝修复」三样。

## 8. 成本与顺序

一个 3×2 房间（6 格）的估算：

| 步骤 | 次数 | 单次 | 小计 |
|---|---:|---:|---:|
| 格子出图（2 候选） | 12 | 40 s | 8 min |
| 接缝修复 | 5–7 | 30 s | 3 min |
| 调色/合成 | — | — | 1 min |
| **合计** | | | **约 12 分钟/房间** |

一个区域（6 个房间 + 4 张视差条）：

```text
6 × 12 min + 4 × 1.5 min ≈ 78 分钟
```

这是「一次成型」的成本；重跑通常只发生在 1–2 个格子。

**建议顺序（先验证再放大）**：

1. 拿现有 `room_crossroads`（1792×768）做对照：手摆 blockout → 2 格生成 → 接缝修复 → 对比实机。
2. 换成 3×2（6 格）一个房间，跑完一整条：blockout → 6 格 → 修缝 → 抽地砖 → 进 Godot。
3. 做视差四层（整区两张 + 房间两张），验证跨房间走动不露边。
4. 最后才铺区域（全景 + 多个房间）。

## 9. 风险

| 风险 | 表现 | 对策 |
|---|---|---|
| 模型不守 blockout | 平台位置被画歪，玩法对不上 | blockout 用高对比纯色；参考图权重靠「第 1 张定结构」的链路特性；实在不行改用 inpaint 只在空隙里补 |
| 接缝修不好 | 缝变糊、出现重影 | 遮罩带宽 32–48 px 起，别一次修太长；修完再对比梯度 |
| 64px 地砖不可平铺 | 抽出来的砖有明显接缝 | 地砖单独出一张 2048×2048 模块表（`docs/06` 已有此规格），格子图只提供色板与材质参考 |
| 远景放大发虚 | 远景像糊了一层 | 远景本来就该低对比；加一层雾/暗角压住；必要时用 `repeat_size` 或镜像拼接 |
| 风格漂移 | 房间之间像两个游戏 | 每格都带「区域全景」当第 2 参考图 + 固定色板与光照方向；导出后做一次整区 LAB 匹配 |
| 成本超预期 | 一个区域 2 小时 | 先做 1 个房间验证；候选数从 2 降到 1，靠接缝修复兜底 |

---

## 10. 一句话

**把「大地图」拆成：一张全景定调、四张视差条定远景、六个格子定一个房间、一套地砖定玩法。**
接缝不是靠「生成得更准」解决的，是靠「让缝落在结构上 + 局部重绘」解决的。

## 11. 接缝实验：实测五次，结论有变

在 MiraForge 里真跑了 5 组（场景 3「矿道枢纽 · 单屏实验」，左格固定用 `scenes/3/images/20/26_0.png`，1280×720，重叠 160 px，切口 x=1120）。脚本在 `data\_exp_seam*.py`，对比图 `data\_seam*_before.png` / `data\_seam*_after.png`。

| 版本 | 引导方式 | 接缝跳变 / 中位（比值） | 修缝后 | 主要失败 |
|---|---|---|---|---|
| v1 | 只给左格当参考，提示「延续右侧」 | 重叠带 `\|ΔL\|=48.34` | 只动了 48 px，视觉无变化 | **把整个场景重画一遍**，拱门/石柱/蘑菇重复 |
| v2 | 左格 + 水平镜像 | 6.97 / 4.23 = 1.65 | 4.22 / 4.18 = 1.01 | 缝能修，但**镜像感漏进成图**：根系、拱门左右对称重复 |
| v3 | 逐格手绘 blockout + 左格 | 11.69 / 3.53 = 3.31 | 2.63 / 3.47 = **0.76** | 不重复、布局跟得住，但**邻格高度对不上**（左格台面 y≈250，右格从 y≈448 起）；画面偏暗；blockout 里的青色圆点被画成气球 |
| v4 | **整房连续 blockout** 再按格裁 + 左格 | 11.37 / 3.19 = 3.57 | 5.23 / 3.11 = 1.68 | 共享边天然一致了，但**平涂色块的灰色质感漏进成图**（拱门被直接画成灰色弧） |
| v5 | 左格右缘「行向拉伸 + 台面亮度延续」当引导（美术先行） | 31.17 / 4.33 = 7.20 | 11.82 / 4.18 = 2.83 | 引导只含边缘信息 → **右格又把左格抄了一遍** |

### 由此改写的结论（比第 9 节更硬）

1. **「切一块下来让模型补」这条路是死的。** 无论给不给引导，只要结构信息不够，模型要么重复邻居、要么重复自己；v1 的重叠带差异 48 灰阶说明它不是「续画」，是「重画」。
2. **能驱动「新的但接得上」的只有结构性引导**：整房 blockout 覆盖整格、且重叠那一列与邻居共享（v3/v4 都做到了不重复、布局跟得住）。只给边缘（v5）必然退化成复制。
3. **平涂 blockout 会把自己的质感带进成图**。引导要画成「暗块 + 雾」的抽象 massing（低对比、无细节、明确告知「只是占位」），不要用中灰色实心块 —— v4 的拱门就是这样被画成灰弧的。
4. **不要指望像素级对齐**：模型对 64 px 网格没有任何概念，跨格台面高度会漂几十像素。所以**碰撞与平台要按成图来写，不是按 blockout 来写**——blockout 只用来约束「大致是什么形状的关卡」。
5. **修缝只能修「接不上」的观感，修不了结构错位**。v3 数值已到 0.76 但视觉上仍有台阶断层，就是证据。修缝遮罩 32–48 px 就够，别越修越糊。

### 落到流程上的修正

```
区域全景（定调、当地图界面）
├─ 视差四层：整区一条，生成后放大（天然无缝）
└─ 房间：整房 blockout（抽象 massing）→ 按 1280×720 切格（重叠 160px）
        → 每格 edit：blockout 格 + 已完成的邻格 + 区域全景
        → 拼接 → 64px 窄带 inpaint 修缝 → 从成图反推碰撞与平台
```

顺序上最关键的一句：**美术先行、碰撞跟随**。想让「图去匹配关卡」，只有手摆 blockout + 人工修正才成立；想让「关卡去匹配图」，就要在成图上量平台高度，再写 `StaticBody2D`/`TileMap`。

（Godot 侧的现实约束见 `docs/05_地图与场景美术规范.md`：64×64 tile、单跳 181 px、二段跳 362 px。成图里每段台子的间距与高差按这些数去量，比按 blockout 去改图省事得多。）

### 11.1 补测：按「宽遮罩 inpaint」修缝，确实成立

用户自己拿一张手工拼接图（1280×720，接缝在 x≈565，左右两侧明度差明显）在图片编辑里跑了一次 inpaint：模型 `qwen_image_21_turbo`、4 张候选、总耗时 **35 秒**，提示词就一句「请将这张图中间拼接的部分进行调整，使其自然过渡，其它地方保持不变」。

拿程序量了一下（`data\_seam_measure.py`、`data\_seam_where.py`）：

- 原图接缝两侧列均值 19 → 35 → 40（硬阶跃）；遮罩覆盖 **x≈460–625（约 165 px）**。
- 4 张候选改动面积 11–13%，改动区间都在 460–625，**其余像素逐位未动**。
- 阶跃被替换成连续的根幕与雾，肉眼看不到接缝；前景剪影也自然接上了。

这条和我在 v1–v5 里的差别只有一个：**遮罩宽度**。我此前用 32–48 px，只能抹平「亮度台阶」；跨过 120–200 px 时，模型有足够空间把两侧的材质、笔触、雾的梯度重新长到一起。所以第 9 节那条「32–48 px 起」要改成：

| 缝的类型 | 遮罩宽度 | 说明 |
|---|---|---|
| 只是明度/色温不一致 | 32–48 px | 窄带就够，改得越少越安全 |
| 两侧内容不同、结构要续 | **120–200 px** | 宽遮罩让模型有地方长新内容；v3 的 0.76 也是宽遮罩的结果 |
| 结构高度对不上 | 不要修 | inpaint 只会把它画得更糊，必须回到「按成图写碰撞」 |

由此这条流程可以定稿：**拼接本身不是问题，修缝也不是问题（35 秒/4 张）；唯一要人管的是「每段台子的高度与间距」**，而那正好是从成图里量、写进 Godot 的活。

### 11.2 整房 3×2 实测：单格可用，拼整间房不行

按上面的配方真跑了两遍整房（3 列 × 2 行、1280×720 一格、重叠 160 → 3520×1280；脚本 `data\_exp_room.py` / `data\_exp_room2.py`，场景 4、5）。

| 版本 | 每格的第二张参考 | 竖缝（修前） | 横缝（修前） | 结果 |
|---|---|---|---|---|
| v1 | 完整邻格 | 7.9× / 7.9× | 4.9× | **每格都抄成同一个样子**：拱门、根幕、蘑菇重复 6 次 |
| v2 | 邻格最右 160 px 细条 + 每格不同地标 | 3.3× / 3.8× | 10.0× | 上排像样，**下排把色块里的大块深色平涂照抄成了灰黑板** |

v2 的上排单格质量其实很好（楼梯、根幕、拱门、荧光植物都在，剪影可读），说明「整格 blockout → 一张 1280×720 的场景板」这一步是成立的；崩在**拼**：

1. **大块平涂会被当真**。我的 blockout 在每段石台下面铺了 300 px 的深色填充，下排格子直接把它画成了灰黑大板子——它不区分「这是空的」还是「这是墙」。blockout 里的深色块要小、要碎、要带噪声渐变，宁可留白让模型自己长雾。
2. **横缝 10× 是最难的一处**：上下两格的地平线、光照角度、雾的密度都不同，宽遮罩也压不住；竖缝 3.3× 尚且可修。
3. **尺寸必须显式归一**：edit 出来的图是 **1280×704**（不是 720），照 720 直接拼会留下一圈 16 px 的错位带。拼之前统一 `resize` 到目标尺寸。
4. 给了完整邻格 → 抄邻居；只给 160 px 细条 → 不抄了，但仍会抄自己的 blockout 平涂。

**结论（正式写进流程）**：整房「切格生成再拼」只能出概念图/氛围图，不能当关卡底图。可生产的单位是**一屏 1280×720 的场景板**；更大的房间应该在引擎里用「一屏背景 + 模块化地形（平台件、柱件、拱件、蘑菇丛）+ 每房一个地标」去拼，这本来就是 `docs/05` 的写法，而且**模块化拼装没有接缝问题**——重叠 16–32 px 直接叠，不需要 inpaint。

### 11.3 模块路线实测：成立

用场景的透明出图能力做了 6 个模块件（场景 6「模块件实验」，脚本 `data\_exp_modules.py`，全部 `qwen_image_21`、单张 25 步、**每个 30–60 秒**）：

| 模块 | 尺寸 | 模式 | 透明占比 | 用途 |
|---|---|---|---|---|
| platform_a | 640×352 | RGBA | 11.2% | 平顶石砌平台（左右切边可平铺） |
| platform_b | 640×352 | RGBA | 23.3% | 带三级台阶的平台 |
| pillar | 320×704 | RGBA | 27.5% | 断裂石柱（柱础贴底） |
| arch | 640×704 | RGBA | 27.4% | 废弃石拱门（拱洞透明） |
| mushroom | 320×320 | RGBA | 35.4% | 发光蘑菇丛（底部贴底） |
| roots | 320×704 | RGBA | 18.9% | 垂挂根幕（顶部贴顶） |

关键实测数据：

- **每一张都是真 alpha**（`alpha extrema (0,255)`），背景像素 RGB 也被清干净，直接叠图不会带底色；
- **平台的顶面是平的**：`platform_a` 沿 600 列量顶边 y，`min=127 max=132 标准差 0.65px` —— 引擎里就是这个模块的碰撞面，不需要再从成图里猜；
- **模块之间没有接缝**：叠图时按 640 的整数倍摆、重叠 16–32px，视觉上直接连上（整房 mock `_mods_room.png` 里地面 6 段完全看不出接口）；
- 拼装一张 **3520×1280 的整房**只是 6 次生成（≈4 分钟）+ 一次 PIL 合成，**不需要 inpaint**。

会看到的问题（都不是接缝问题）：

1. **重复感**：同一个 `platform_a` 摆 6 次，柱子 4 根一样。解决办法是每个模块出 3–4 个变体（`platform_a1/a2/a3`，裂纹、缺口、苔藓密度不同），拼装时随机取；
2. **模块边界要约定**：平台件「底边留空、顶面贴某个固定 y」，柱子「底面贴底边」，根幕「顶边贴顶」，蘑菇「底边贴底」——生成时就在提示词里写死，拼装才不用猜；
3. **背景仍然是空的**：模块只解决「前景/地形」，雾、光、远景还得单独一层（视差那几层）。

这条路线比「切格拼大图」好在：**接缝问题被消灭了**，质量上限由单个模块决定，而单个模块的质量是达标的；成本是一次性攒一套 kit（12–20 个件），之后整区复用。

### 11.4 更省的做法：一张透明总表，按格切

把「每个模块单独生成」换成「一张透明 2×2 总表」实测（场景 7「模块总表实验」，脚本 `data\_exp_sheet.py` / `_exp_sheet_assemble.py`）：

- 一次 `qwen_image_21` 出图 1280×720、40 秒，**四个部件各占一格、互不接触**，整张图 82.3% 面积是 alpha=0；
- 按 2×2 网格切，每格都只有**一个主连通块**（实测 1/1/5/2 个连通块，>800px 的只有 1 个），不需要 SAM，直接 alpha bbox 裁剪即可；
- 四件同光、同材质、同色板 —— 这正是分开生成最难保的一点。

拿这四件拼一张 3520×1280（`_sheet_room.png`）也能用，但暴露三个必须处理的点：

1. **透明区的 RGB 是紫色残留**（alpha=0 但 RGB≈紫），且中间还留了一条极淡的半透明横带。切完先做 alpha 清理：`alpha<32 → 0`、`alpha=0` 的像素 RGB 清零、`alpha<200 且偏紫` 的像素也清掉（清理前后透明占比 82.3% → 82.5%，视觉上干净得多）。
2. **平铺接边不平**：把平台件左右铺 9 段，接缝跳变 0.26–3.93，而图中位 0.82 —— 有 4 处肉眼可辨。修法：两端各裁 8–16 px 让接边落在侧壁内部；或隔段水平翻转；或重叠 24–32 px。
3. **单件细节只有总表的 1/4**：总表里平台件只有 367×110，单独生成是 640×352。总表适合出「中景/远景的小件、装饰件、道具」；平台、柱、拱这类占屏面积大的主件，还是单独出一张、用总表当第二参考图。

所以最终形态是三层搭配：

| 用途 | 做法 | 成本 |
|---|---|---|
| 定风格 / 色板 | 一张带环境的风格图（或现成的满意成图） | 1 次 |
| 小件、装饰、道具 | 透明 2×2 或 3×3 总表，按格切 | 1 次 = 4–9 件 |
| 主件（平台 / 柱 / 拱 / 大蘑菇丛） | 单独 640×352 或 320×704，带总表当参考 | 1 次 = 1 件 |
